# Task 01 — Schemas and the one-street fixture

**Build-order step:** 1 (and the fixture half of step 2)
**Depends on:** nothing
**Produces:** `crates/schema/` (Rust types + serde + JSON Schema export), golden
JSON fixtures, the hand-built one-street plant.
**Load:** `CLAUDE.md`, `docs/physics.md`; for channel plans and capabilities,
`docs/reference/phy-docsis31.md` and `docs/reference/collection-management.md`.

## Goal

Define the seven data contracts everything else reads, as Rust types with serde,
and prove them with golden fixtures. Nothing else: no sim, no optimizer, no
server. The session ends when `cargo test` passes and `fixtures/` round-trips.

## Deliverables

### 1. Workspace skeleton

```
Cargo.toml              # [workspace] members = ["crates/*"]
crates/schema/          # this task
fixtures/
  schemas/              # golden JSON per type, generated by a test
  library/
    generic.json        # the component library
  profiles/
    d31_lowsplit_1002_iccap.json
    d31_highsplit_1218_rpd.json
  policy/
    default.json        # one entry per cause class
  one_street/
    plant_lowsplit_iccap.json
    plant_highsplit_rpd.json   # same topology; root element and profile_ref differ
    faults.json         # a FaultSet with a seed and no faults
    fault_examples.json # one example of each fault class, not applied
    environment.json    # one sample: t = 0, 20 °C air and ground, no rain
```

Dependencies allowed in `schema`: `serde`, `serde_json`, `schemars` (JSON
Schema export), `uuid`, `thiserror`. Nothing else. That means two small local
types: `Timestamp` (i64 seconds of simulated time, passed in, never read from the
system clock) and `Complex { re, im }` for pre-eq coefficients. Any UUID is derived
from stable inputs (v5), never random (v4), per the determinism invariant.

### 2. The seven schemas

Each lives in its own module, has a `SCHEMA_VERSION: &str` constant, derives
`Serialize, Deserialize, JsonSchema, Debug, Clone, PartialEq`, and has a
doc-comment on every field stating units (see `CLAUDE.md` style rules). Every
top-level file carries `schema_version`, so a migration can identify it. Level
fields also state their reference bandwidth, which is 6 MHz unless the field says
otherwise (see `docs/physics.md` conventions and §4.2). All floats must be finite:
JSON has no `Infinity` or `NaN` and `serde_json` writes them as `null`, which
breaks the round-trip test, so use an explicit variant or `Option` instead.

**a. `plant` — the plant graph.**
One plant file is one node's tree, which is one service group; a region is a list
of these (see Deferred). The plant carries `service_group: ServiceGroupId` and
`profile_ref: ProfileId`, so each node can have its own profile, and `origin:
Synthetic|Field` (invariant 11).
A directed tree rooted at a `Node` (or `Rpd` in the DAA variant). Tree elements:
`Node`, `Rpd`, `Amp`, `Tap`, `Splitter`, `DirectionalCoupler`, `PowerInserter`,
`Terminator`, `Modem`. Edges are `Span { cable_ref, len_ft, installation:
Aerial|Underground, power_passing: bool }`, `Drop { cable_ref, len_ft }` or `Direct`
(a part mounted on a port, such as a terminator, with no cable). Each edge records
the port it leaves and enters, since off-path echoes and FDX need port identity and
it can't be rebuilt later.
Every element has `id: ElementId` (a stable human-assigned string such as `amp-1`),
`component_ref: ComponentId` (into the library), `geo: Option<LonLat>`, `ports`, and
`record_status: Designed|Built|Imported`.
`Node`, `Rpd` and `Amp` also have `return_atten_db`, default 0 (§7.3). Modems hang off
tap ports via drops.
Power is a separate overlay, not part of the tree: `power_supplies: Vec<PowerSupply {
id, component_ref, feeds: ElementId, geo }>`.
`ModemBinding { element_id, pseudonym }` links a plant modem to a hashed identity for
step 7; raw addresses never appear in the schema (invariant 10).
Include `fn validate(&self, library: &ComponentLibrary, profile: &Profile) ->
Result<(), Vec<PlantError>>` checking: tree (no cycles, one root), every tap port
used at most once, every referenced component id exists in `library`, every `Span`
and `Drop` has len_ft > 0, `profile_ref` is `profile`'s id, and the root element
(`Node` or `Rpd`) matches `profile.node_kind`.
Include `fn parts_list(&self) -> Vec<PartsLine { component_ref, quantity, total_len_ft:
Option }>` too. It is derived, never stored (invariant 1).

**b. `profile` — architecture profile.**
`ProfileId`, `docsis: D30|D31|D40Esd|D40Fdx`, `band_plan: Vec<BandSegment { lo_mhz,
hi_mhz, direction: Us|Ds|Both }>` (segments rather than one upstream and one downstream
range, since D4.0 has two upstream bands and FDX shares one), `channel_plan`,
`max_cascade: u8`, `max_homes_passed`,
`design_levels: {out_dbmv_at_hi, tilt_db, psd_spread_max_db, modem_in_min_dbmv_by_qam,
modem_in_max_dbmv, modem_in_total_max_dbmv, us_node_in_target_dbmv}` (the upstream
target is per 6.4 MHz), `fec: Vec<{ qam, thr_db, req_cnr_db, req_cnr_above_1002_db: Option,
sc_qam_thr_db: Option }>` (§4.6),
`modem_behavior: { tx_saturation: Clamp, ranging_spacing_s, reregistration_s }` (§7.2,
§7.4), `node_kind: Analog|Rpd`, `capability: CapabilitySet`.

`channel_plan` holds SC-QAM channels, OFDM channels and OFDMA channels as separate
types, each with a stable `channel_id`. OFDM and OFDMA carry first and last active
frequency, FFT size checked against subcarrier spacing per direction, `cp_us`,
`rolloff_us` and data profiles with their modulation. OFDM also carries NCP modulation
(QPSK, 16-QAM or 64-QAM); the PLC is always 16-QAM, so it isn't a field.

`CapabilitySet` says which observation fields exist, and how: RxMER file and summary
separately; channel estimate file and summary; OFDMA pre-eq file and summary; SC-QAM
pre-eq; FBC by file or SNMP, with its covered band; per-profile FEC; PLC and NCP
counters; 6 MHz band power; upstream RxMER file and summary; upstream spectrum capture;
one flag each for `v_in`, `i_draw`, `temp_c`, `status`, `out_level`; and the access path
(`CmSnmp`, `CmTftp`, `CmtsSnmp`). A modem also has a `CapabilitySet`, and a function
returns the effective set, the intersection of profile and modem, because generations
mix on one node.

Ship two instances. Channel plans are plausible assumptions (approx), to confirm with
an operator:

| | `d31_lowsplit_1002_iccap` | `d31_highsplit_1218_rpd` |
|---|---|---|
| Band plan | 5–42 up, 54–1002 down | 5–204 up, 258–1218 down |
| Levels (§3.1) | 50 dBmV, 14 dB tilt | 52 dBmV, 12.1 dB tilt |
| `us_node_in_target_dbmv` | 8 | 10 |
| Node | `Analog` | `Rpd` |
| Downstream | 32 SC-QAM, one 192 MHz OFDM at 810–1002 | 32 SC-QAM, two 192 MHz OFDM up to 1218 |
| Upstream | 4 SC-QAM of 6.4 MHz | 4 SC-QAM of 6.4 MHz, one 96 MHz OFDMA at 108–204 |

Both use 4K FFT (50 kHz) downstream and 2K FFT (50 kHz) upstream, 2.5 µs cyclic prefix,
1.25 µs roll-off, data profiles of 256, 1024 and 4096-QAM, and 16-QAM NCP.

**c. `component` — component library entry.**
`ComponentId`, `version: u32`, `class: Node|Rpd|Amp|Tap|Splitter|DirectionalCoupler|
PowerInserter|PowerSupply|Terminator|Cable|Drop|Modem`, `vendor`, `model`,
`source_url: Option`, `spec_confidence: Datasheet|Generic|OperatorSupplied`,
`rated_lo_mhz`, `rated_hi_mhz`, and a `spec` enum per class carrying exactly the fields
`docs/physics.md` needs (a `ComponentLibrary` is a collection of these entries).
Qualification isn't stored: it is a function, `qualifies(&Component, &Profile) -> bool`,
of the rated band and the band plan and, for actives, `duplex`. A stored list would be a
derived value kept as input (invariant 1), and ratings couldn't be rebuilt from it later.

The profile holds targets, and a component holds capability. So output level, tilt and
supply voltage each live in one place: target level and tilt in the profile, what an
amp can deliver in its spec, and supply voltage on the power supply.

- Cable and Drop: `atten_a`, `atten_b` (§1.1), `k_temp` (§1.2), `v_f` (§1.3), `r_loop_ohm_per_kft` (§1.4)
- Amp and Node: `max_out_dbmv_at_hi`, `max_gain_db`, `min_in_dbmv`, `nf_db`, `return_nf_db` (§7.3), `ctb_ref_db`, `cso_ref_db`, `cin_ref_db`, `ref_out_dbmv`, `return_gain_db` (§7.1), `agc_range_db` (§3.4), `return_loss_db` (§5.1), `duplex: Diplexed { splits: Vec<{ us_hi_mhz, ds_lo_mhz, group_delay_ns: Vec<{ f_mhz, delay_ns }> }>, remote_switchable: bool } | FullDuplexEc { group_delay_ns }` (§5.6), `power_w`, `v_min`
- Node only: `optics_cnr_db`, `us_optics_snr_db` (§4.5, §7.3)
- Rpd: the Amp and Node fields for its RF module, without the optics fields, plus `supported_pnm_tests`
- Tap: `ports`, `tap_value_db`, `insertion_loss: Vec<{ f_mhz, loss_db }>`, `tap_loss: Vec<{ f_mhz, loss_db }>`, `port_isolation_db`, `return_loss_db` (§2.1, §5.1), `power_passing`
- Splitter and DirectionalCoupler: per §2.2
- PowerInserter: `i_rated_a`, `power_passing`
- PowerSupply: `v_out`, `i_rated_a` (§6.3)
- Terminator: `return_loss_db`
- Modem: `generation: D30|D31`, `impl_mer_db`, `nf_db` (§4.5), `return_loss_db` (§5.1), `tx_max_total_dbmv` (§7.2; the only stored transmit limit, because per-channel limits are derived), `capability: CapabilitySet`

Ship `fixtures/library/generic.json` with about 14 entries sufficient for the fixture,
including one D3.0 and one D3.1 modem and one RPD, every one tagged `spec_confidence:
Generic`, with values from `docs/physics.md`.

**d. `fault` — fault parameterizations.**
One enum variant per row of `docs/physics.md` §8, with the parameters listed there and
its `Location` and `Schedule` types, plus `onset: Instant|Ramp { start: Timestamp, end:
Timestamp }` on every fault. A `FaultSet { schema_version, seed: u64, faults: Vec<Fault> }`.

**e. `observation` — what the sim emits.**
Per `docs/physics.md` §9: `ModemObservation`, `ActiveObservation`,
`ServiceGroupObservation`, each with `t: Timestamp`, `schema_version`, `origin:
Synthetic|Field` and the `element_id` or `service_group` it describes. Channel records are self-describing, as §9
says, so a record can be read without the channel plan then in force. Fields that a
capability mask can remove are `Option`. This layer holds absolute values only; the
feature layer is step 4.

**f. `environment` — inputs that are neither plant nor fault.**
Per `docs/physics.md` §10: `Environment { schema_version, samples:
Vec<EnvironmentSample> }`, with `EnvironmentSample { t: Timestamp, temp_c, ground_temp_c,
rain_mm_per_hr }`. One environment applies to one plant.

**g. `work_order` — the output contract, and how it's made.**
`CauseClass`, one variant per fault class in §8, plus `Unknown`.
`PolicyTable { schema_version, entries: Vec<PolicyEntry { cause: CauseClass,
component_class, action, parts: Vec<String>, crew }> }`: the operator-owned table from
cause and component to fix.
`WorkOrder { schema_version, id, service_group, t, element_id, geo, cause: CauseClass,
parameters: Fault, confidence: f32, affected_modems: u32, action, parts: Vec<String>,
explanation, status: Proposed|Dispatched|Completed|Verified|NotVerified }`. `id` is a v5 UUID of service group, `t`, element and cause. `explanation`
is rendered from a template, not generated text.

### 3. The one-street fixture

Two plant files with the same topology, all spans .500 and aerial, and all taps 4-port:
root → 1,200 ft → `Amp` → 400 ft → 23 dB `Tap` → 300 ft → 17 dB `Tap` → 100 ft → `Amp` →
400 ft → 23 dB `Tap` → 300 ft → 17 dB `Tap` with a `Terminator` on its through port by a
`Direct` edge. The root is a `Node` on low-split and an `Rpd` on high-split.

Two modems per tap on RG6 drops (8 modems), in order: 80 and 150 ft, 80 and 120 ft, 80
and 150 ft, 80 and 120 ft. The 80 ft modems are D3.0 and the others D3.1, so both
generations share a tap. One `PowerSupply` (90 V) at the root end feeds both amps.
Geo coordinates along a straight east-west street at an arbitrary Front Range location
(placeholder; the optimizer replaces this later). Both plants are `Synthetic`, and every
element is `Built`.

This is the plant that `docs/physics.md` §3.2's, §4.5's and §7.2's oracles are computed
on; the first 120 ft modem is the single-modem oracle, and the sim task will assert
those levels. Generic amps need a `min_in_dbmv` of 18 or lower at 1218 MHz and a
`max_gain_db` of at least 34, so both amps stay in spec at 45 °C.

### 4. Tests

- Round-trip: every schema type `serialize → deserialize → eq`.
- Golden: `fixtures/schemas/*.json` are regenerated by a test behind
  `--features regen`; the default test asserts they are unchanged.
- `plant::validate` passes on both fixture plants with their profiles, and fails on
  four hand-broken variants (cycle, dangling component ref, zero-length span, root kind
  that disagrees with the profile's `node_kind`).
- `parts_list` on the fixture returns 1 root, 2 amps, 2 of each tap, 1 terminator, 1
  power supply, 4 of each modem, 2,700 ft of .500 and 860 ft of RG6.
- `qualifies` accepts every generic part for at least one shipped profile and rejects a
  part whose rated band doesn't cover the band plan.
- The effective capability of the D3.0 modem has no OFDM fields on either profile.
- FFT size and subcarrier spacing that disagree fail validation.
- JSON Schema export for every type writes to `fixtures/schemas/*.schema.json`
  (these are what the TypeScript UI and Python ML code will consume).

- Downstream OFDM details the reference notes suggest but physics.md doesn't use yet: time
  interleaver depth, exclusions, PLC location, upstream minislots and pilot patterns.

## Decisions made during the task

- **Named table points, not tuples.** Loss and group delay tables are `{ f_mhz, loss_db }` and
  `{ f_mhz, delay_ns }`, since CLAUDE.md requires units in field names.
- **Group delay sits on the split.** The amp fixture serves both profiles, and its band-edge
  delay moves with the diplexer, so one table per active would misplace it on one of them.
- **`qualifies` treats modems differently.** Plant parts must cover the whole band plan. A modem
  only has to reach part of each direction, because a D3.0 modem shares a high-split node
  (§11). Otherwise the fixture's D3.0 modems wouldn't qualify on the high-split plant.
- **`rated_lo_mhz` and `rated_hi_mhz` are `Option`,** and `None` only on a power supply, which
  has no RF path.
- **`class` is the tag of `spec`,** so the two can't disagree.
- **`feeds` is where current enters the tree.** It flows on along power-passing edges, so the
  fixture's supply feeds the root and reaches both amps.
- **`validate` checks more than listed:** ports exist, components are the right class, tap port
  counts match, modems are on drops, and bindings name modems. `Profile::validate` also checks
  cyclic prefix and roll-off options, active range, the subcarrier grid and the band plan.
- **`RegState` covers only what §7.4 moves through.** An adapter collapses the other
  `CmRegState` values into these (invariant 2).

Values with no source, all to confirm: `max_homes_passed` 500, `ranging_spacing_s` 15,
`reregistration_s` 60, the channel placements, the fixture's `group_delay_ns` tables (set at
step 7 against [PNM-HFC Table 12]), and the D3.0 modem's `impl_mer_db` 40 and FBC band.
